1. What is RKE2 Deep Monitor?

RKE2 Deep Monitor is a continuous cluster health monitoring tool for RKE2 Kubernetes clusters. It runs 70+ checks every collection cycle covering:

  • Infrastructure — Node health, CPU, memory, disk, temperature, network interfaces, NIC speed/duplex, link flaps
  • Control Plane — API server latency, etcd DB size/latency/leader stability, scheduler, controller-manager
  • Certificates — TLS certificate expiry countdown with visual timeline
  • Storage — Ceph cluster health, OSDs (latency, utilization), pools, PGs, PVs/PVCs, recovery, scrub
  • Workloads — Pods, deployments, daemonsets, statefulsets, OOM kills, evictions, probe failures
  • Security — Privileged containers, RBAC audit, resource limits, image tag policy, network policies
  • Network — CNI health, DNS, ingress, NIC errors/drops, inter-node latency, bandwidth, bonding, MTU
  • Hardware — SMART disk health, IPMI sensors (fans/PSU), PCIe AER errors, temperature sensors
  • Capacity — Resource headroom, pod capacity, growth trend forecasting, resource waste detection
  • Cost Optimization — Unused/idle resource detection (stale pods, zero-replica deployments, unused PVCs, idle pods)

Data is stored for 7 days (configurable) on persistent storage (50Gi SSD) for trend analysis and pattern detection. Dashboard auto-refreshes every 30 seconds.

3. Glossary — Terms & Abbreviations

Common terms used throughout the dashboard and what they mean.

TermFull NameWhat it is
NICNetwork Interface CardThe physical or virtual network adapter in a server that connects it to the network. Each server typically has 1 or more NICs (e.g. eth0, ens18).
NIC SpeedLink SpeedThe negotiated speed of the network connection — e.g. 1000Mb/s (1 Gbps) or 10000Mb/s (10 Gbps). Lower than expected speed may indicate a bad cable or switch port.
DuplexFull/Half DuplexFull duplex = data can flow both directions simultaneously. Half duplex = one direction at a time. Always should be "Full" — half duplex indicates a cable or auto-negotiation problem.
MTUMaximum Transmission UnitLargest packet size (in bytes) the network can carry. Standard is 1500. Jumbo frames use 9000. All nodes in a cluster must have the same MTU or connectivity breaks.
Link FlapsCarrier ChangesHow many times the NIC link went up and down since boot. High number means an unstable physical connection — bad cable, loose connector, or failing switch port.
SMARTSelf-Monitoring, Analysis and Reporting TechnologyBuilt-in health monitoring on hard drives and SSDs. Reports if a disk is about to fail. "PASSED" = healthy, "FAILED" = disk dying and needs replacement immediately. "N/A" on VMs.
IPMIIntelligent Platform Management InterfaceHardware management system built into physical servers. Monitors fan speeds, power supplies, temperatures, and voltages via the BMC (Baseboard Management Controller). Not available on VMs.
BMCBaseboard Management ControllerA small dedicated processor on the server motherboard for remote hardware management (iLO, iDRAC, IPMI). Allows monitoring even when the OS is down.
PSUPower Supply UnitThe component that converts AC power to DC for the server. Servers often have 2 PSUs for redundancy. IPMI monitors their status.
PCIe AERPCI Express Advanced Error ReportingError detection for PCI Express bus (connects GPUs, NICs, storage controllers). Errors indicate hardware faults — bad PCIe slot, failing card, or motherboard issue.
OOMOut of MemoryWhen a process or container uses more memory than allowed, the Linux kernel kills it (OOM Kill). Indicates the container needs higher memory limits or has a memory leak.
FD / File DescriptorsFile DescriptorsHandles the OS uses for open files, sockets, and pipes. Each process has a limit. Running out of FDs causes "too many open files" errors and application crashes.
Zombie ProcessDefunct ProcessA process that has finished but its parent hasn't acknowledged it yet. They consume a process table slot. High count indicates a buggy parent application not reaping child processes.
dmesgKernel Message BufferThe Linux kernel log. Contains hardware errors, OOM events, driver issues. The monitor checks for critical messages like OOM kills and hardware errors.
Load AverageSystem LoadAverage number of processes waiting for CPU over 1/5/15 minutes. A load of 1.0 on a 4-core machine means 25% busy. Load ratio = load / cores — above 1.0 means CPU is overloaded.
LatencyNetwork DelayTime for a network packet to travel between two points, measured in milliseconds (ms). Low latency (<1ms) = good. High latency (>50ms) = slow network affecting cluster communication.
etcdetcd Distributed KV StoreThe database that stores all Kubernetes cluster state (pods, services, secrets, configs). If etcd is unhealthy, the entire cluster stops working.
CephCeph Distributed StorageA distributed storage system used by Rook-Ceph in Kubernetes for persistent volumes. Provides block, filesystem, and object storage.
OSDObject Storage DaemonA Ceph process managing one physical disk. Each disk in the Ceph cluster runs one OSD. OSD latency directly impacts storage performance.
PGPlacement GroupCeph organizes data into placement groups. PGs should be "active+clean". Degraded or undersized PGs mean data isn't fully replicated.
PV / PVCPersistent Volume / Persistent Volume ClaimPV = a piece of storage provisioned in the cluster. PVC = a request for storage by a pod. PVCs bind to PVs. Unbound PVCs mean storage is unavailable.
CNIContainer Network InterfaceThe networking plugin for Kubernetes (Calico, Canal, Cilium, Flannel). Provides pod-to-pod networking, network policies, and IP management.
PDBPod Disruption BudgetKubernetes resource that limits how many pods can be down during maintenance (node drain, upgrade). Without PDBs, all replicas could be evicted at once.
RBACRole-Based Access ControlKubernetes permission system. Controls who can do what. Excessive cluster-admin bindings are a security risk.
CrashLoopBackOffPod Crash LoopA pod that keeps crashing and restarting. Kubernetes backs off the restart interval each time. Indicates a misconfiguration, missing dependency, or application bug.
BondingNIC Bonding / TeamingCombining two or more physical NICs into one logical interface for redundancy or bandwidth. If one cable fails, traffic continues on the other.
NVMe / SSD / HDDStorage Device TypesNVMe = fastest (connects via PCIe). SSD = fast (connects via SATA). HDD = spinning disk (slowest). NVMe is preferred for etcd and Ceph OSDs.

6. Alerts & Notifications

How alerts work:

  1. Define alert rules on the Alerts page (e.g. memory_percent > 80 warning, > 90 critical).
  2. Every scrape cycle (default 30s), the engine evaluates rules against collected metrics.
  3. When a threshold trips, the alert is shown on the dashboard and dispatched to each channel mapped to that rule. The cluster name (Settings → Cluster) is included in every notification title.
  4. When the metric returns under the threshold, a RESOLVED notification is sent through the same channels.

Setting the cluster name

The cluster name appears in all alert titles and report headers. Configure it once at Settings → Cluster → Cluster Name. The value is stored in the dashboard's database and overrides the legacy CLUSTER_NAME env var. If neither is set, alerts say "cluster".

Step 1 — Add a notification channel

Go to Settings → Notification Channels. Each channel needs a name, a URL, and an optional category filter (leave blank to receive all alerts). Channel type is auto-detected from the URL prefix or domain.

TypeDetected byURL format
Microsoft Teams office.com / microsoft.com https://outlook.office.com/webhook/...
Slack hooks.slack.com https://hooks.slack.com/services/T.../B.../...
Discord discord in URL https://discord.com/api/webhooks/<id>/<token>
PagerDuty pagerduty.com https://events.pagerduty.com/v2/enqueue (routing key in URL)
Email (SMTP) scheme smtp:// or smtps:// smtp://user:pass@host:587?from=a@x.com&to=b@y.com[,c@y.com]
Generic any other https:// Any URL accepting JSON POST — receives {text, alert}

Microsoft Teams setup

  1. In Teams, open the channel you want notifications in → click ... next to its name → Workflows → Post to a channel when a webhook request is received.
  2. Sign in, pick the team and channel, click Add workflow, copy the URL it gives you.
  3. In the dashboard: Settings → Notification Channels. Name = e.g. Infra Alerts. URL = the workflow URL. Categories = blank (all) or a comma-list like storage,nodes. Click Add, then Test.

Slack setup

  1. Go to https://api.slack.com/apps → Create New App → From scratch → pick a workspace.
  2. Side menu → Incoming Webhooks → toggle On → Add New Webhook to Workspace → choose channel → Allow.
  3. Copy the webhook URL (starts with https://hooks.slack.com/services/...) and paste it into a new channel in the dashboard.

Email (SMTP) setup

Pack all SMTP settings into a single URL. The dashboard parses host, port, credentials, sender, and recipient list from it.

# Gmail (STARTTLS, port 587 — uses an app password, not your login password):
smtp://alerts@example.com:<app-password>@smtp.gmail.com:587?from=alerts@example.com&to=ops@example.com,sec@example.com

# Office 365 (STARTTLS, port 587):
smtp://alerts@yourtenant.onmicrosoft.com:<password>@smtp.office365.com:587?from=alerts@yourtenant.onmicrosoft.com&to=ops@example.com

# SES SMTP / SendGrid / generic SSL on port 465:
smtps://<smtp-user>:<smtp-pass>@email-smtp.us-east-1.amazonaws.com:465?from=alerts@yourdomain.com&to=ops@yourdomain.com

# Internal relay with no auth (set user/pass to empty, no TLS):
smtp://relay.internal.local:25?from=alerts@x&to=ops@x&starttls=0

Query parameters: from — sender address (required); to — comma-separated recipients (required); starttls=1|0 — force or skip STARTTLS on plain smtp:// (default 1). Use smtps:// for implicit SSL on port 465. URL-encode any special characters in the password (e.g. @ becomes %40).

Step 2 — Route a rule to specific channels

When creating or editing a rule, the multi-select Notify Channels dropdown chooses which channels receive that rule's alerts. Hold Ctrl (or Cmd on macOS) and click to select multiple. If you don't pick any, alerts fall back to category-based routing using the channel's category filter.

Per-rule notification levels:

BothSend notifications for warning and critical triggers
Critical OnlySend only when the critical threshold is breached
Dashboard OnlyShow on dashboard but skip all external notifications

Message templates — placeholders for the Message field:

{value}Actual metric value that tripped the rule
{item}Node or item name (e.g. master-1)
{metric}Metric name (e.g. cpu_percent)
{threshold}Threshold value the metric exceeded

Cooldown & resolved notifications

The same alert won't refire within ALERT_COOLDOWN seconds (default 300). When the metric goes back below threshold, a RESOLVED message is sent through the same channels the alert originally fired on, with a green banner.

Testing a channel

Each row in Settings → Notification Channels has a Test button. It dispatches a synthetic info-severity alert through the channel's transport so you can verify connectivity, formatting, and authentication without waiting for a real incident.

8. Features Guide

Server Metrics Dashboard
Pre-built charts for 10 key metrics per node. Select a node or view all nodes overlaid. Supports custom date/time range — e.g. "April 27th 10:00 AM to 12:00 PM". Charts: CPU, Memory, Load, Temperature, Disk, Network Drops, Bandwidth (RX/TX), Pod Count, File Descriptors, Inter-Node Latency.

Unused & Idle Resource Detection
Automatically finds resources wasting cluster capacity:

Stale PodsCompleted/Failed/Evicted pods older than 24 hours
Zero-Replica DeploymentsDeployments scaled to 0 — may be abandoned
Old Completed JobsJobs finished 7+ days ago
Unused PVCsPersistent Volume Claims not mounted by any running pod — wasted storage
Services Without EndpointsServices with no backing pods — orphaned or misconfigured
Idle PodsRunning pods using <1m CPU — may be unused or sleeping

Each finding includes a kubectl cleanup command you can click to copy.

Pod Resource Waste
Detects pods requesting significantly more CPU/memory than they actually use (<20% utilization). Shows total wasted CPU cores and RAM in GiB. Helps right-size pod requests.

Capacity Forecasting
Uses 7 days of historical data to calculate daily growth rate. Projects when CPU, memory, disk, pod capacity, and Ceph storage will be exhausted. Shows: current value, daily change rate, trend direction, 7-day and 30-day projections, days until full. Color-coded: red if <7 days, yellow if <30 days.

Certificate Expiry Countdown
Lists all TLS certificates in the cluster with days until expiry. Color-coded: red if expiring within 7 days, yellow within 30 days. Covers kube-system, rook-ceph, cattle-system, and other namespaces.

Ceph Storage Dashboard
Dedicated page for Ceph monitoring: cluster health and capacity gauge, OSD table with utilization and commit/apply latency, monitor quorum, pool replicas, PG status, recovery/scrub status, PV/PVC binding, CephFS.

Backup & Restore
On the Settings page: Download Backup saves the entire SQLite database file. Restore from File uploads a backup to replace current data (previous DB saved as .pre_restore). Send Report to Webhook sends a status summary to Teams.

HTML & JSON Reports
Download full cluster reports from the Overview page. HTML report includes charts, check summaries, and detailed results. JSON report is machine-readable for integration with other tools.

Auto-Refresh
Dashboard automatically refreshes every 30 seconds as a fallback when WebSocket connection drops. Overview, Nodes, Alerts, and Server Metrics pages stay current without manual refresh.

Timezone Support
All timestamps are displayed in your browser's local timezone. Server stores data in UTC; the dashboard converts automatically.

10. Security & Authentication

Authentication is mandatory. All pages require login. Two roles:

AdminFull access — create/edit/delete alert rules, manage users, clear alerts, trigger collections, backup/restore
ReadView-only — can see all dashboards, checks, metrics, but cannot modify anything

Password Policy

  • Minimum 8 characters
  • At least 1 uppercase letter (A-Z)
  • At least 1 lowercase letter (a-z)
  • At least 1 number (0-9)
  • At least 1 special character (!@#$%^&*)

Session Management

  • Cookie-based sessions, HTTP-only (not accessible via JavaScript)
  • Sessions expire after 7 days
  • Logout button in sidebar

Kubeconfig Security

  • Stored as Kubernetes Secret (encrypted at rest if cluster has EncryptionConfiguration)
  • Mounted read-only with 0400 file permissions
  • Container runs as non-root (UID 1000)
  • RBAC ClusterRole with read-only access (except pods/exec for hardware checks)

User Management (Settings page, admin only)

  • Create users with username, password, and role
  • Change user roles (admin/read)
  • Reset passwords
  • Delete users (cannot delete yourself)
  • Any user can change their own password
